# Examples — 既有项目新增需求样本

这些示例展示 `docs-driven-dev` 在已有项目中如何使用。重点不是格式漂亮，
而是把需求澄清、项目调研、方案确认、实现进度和最终验证放进同一个可追溯工作包。

## 1. 工作包目录

用户说：

> 想给战斗结算界面加一个可展开的奖励详情，先帮我想清楚方案再做。

这已经足够启动流程。用户不需要一开始就写完整背景、涉及文件、
验收标准或非目标；智能体应该通过项目调研和少量追问逐步补齐。

建议创建：

```text
docs/changes/2026-05-19-battle-reward-detail/
  SPEC.md
  ROADMAP.md
  DECISIONS.md
  ARCHITECTURE.md
```

如果调研后发现只是改一份文案表或一处叶子 UI，可以不创建 `ARCHITECTURE.md`，
但需要在 `ROADMAP.md` 记录原因。

## 2. SPEC 片段

```markdown
## 1. 一句话目标

让玩家在战斗结算界面展开查看每个奖励来源和数量，不影响现有一键领取流程。

## 3. 范围

### 3.1 本次要做

- 在结算奖励区域增加展开 / 收起详情入口。
- 展开后显示奖励来源、道具图标、数量和稀有度。
- 保持现有领取按钮、跳过动画和关闭流程不变。

### 3.2 本次不做

- 不改奖励发放逻辑。
- 不新增后端字段。
- 不重做结算界面整体布局。

## 6. 约束与不变式

1. **#1**: 奖励详情只展示已有结算数据，不触发额外发奖。
2. **#2**: 没有详情数据时仍保持旧版结算流程可用。
3. **#3**: 展开状态不得阻塞关闭、跳过动画或继续按钮。

## 8. 验收标准

1. 有多种奖励来源时，玩家可以展开并正确看到每项来源和数量。
2. 无详情数据时界面不报错，并使用旧版汇总展示。
3. 现有结算流程自动化测试或手工回归通过。
```

## 3. ROADMAP 调研记录片段

```markdown
## 2. 调研记录

| ID | 主题 | 发现 | 证据 / 文件 | 结论 |
|---|---|---|---|---|
| R-1 | 结算入口 | 奖励面板由 `BattleResultDialog` 创建并刷新 | `Assets/AsbRes/Lua/Ui/Battle/BattleResultDialog.lua` | 新 UI 入口应接在现有刷新后 |
| R-2 | 奖励数据 | 现有数据只有汇总列表，来源信息来自战斗过程缓存 | `Assets/Code/Battle/Reward/RewardCollector.cs` | 需要确认是否已有来源字段可复用 |
| R-3 | 列表组件 | 同类界面使用 LoopListView2 + PanelBinder | `Assets/AsbRes/Lua/Ui/Common/*` | 按现有列表模式实现 |
```

## 4. ROADMAP 门禁片段

```markdown
### 1.1 实现前必须满足

- [x] 用户目标已用一句话确认
- [x] 范围和非目标已写入 SPEC
- [x] 现有实现、调用点、测试和配置已调研
- [x] 关键约束 / 不变式已写入 SPEC
- [x] 需要的 DECISIONS 条目已记录或标记为阻塞
- [x] 实现步骤和验收方式已写清
- [ ] 用户已确认实现方案
```

只有最后一项得到用户确认后，才进入代码实现。

## 5. DECISIONS 片段

```markdown
## D-001 · Step 3 · 奖励来源数据复用现有缓存而非新增协议字段

**日期**: 2026-05-19

**上下文**:
需求只要求结算界面展示来源详情，调研发现战斗过程内已有来源缓存，
但结算协议当前只携带汇总奖励。

**选项**:
- **A.** 新增协议字段：数据最完整，但影响后端协议和兼容性。
- **B.** 复用本地战斗过程缓存：改动范围小，但需要处理缓存缺失。
- **C.** 仅显示汇总奖励：最稳，但不满足来源详情需求。

**选择**: B

**理由**:
- 满足 SPEC #1，不改变发奖逻辑。
- 不要求后端同步改协议，能把风险限制在客户端展示层。
- 缓存缺失时可按 SPEC #2 回退到旧版汇总展示。

**风险**:
- 如果某些战斗入口没有来源缓存，详情会不可用；按旧版汇总展示降级。

**对应代码 / 文档**:
- SPEC §6
- ROADMAP Step 3
- `Assets/Code/Battle/Reward/RewardCollector.cs`
```

## 6. ARCHITECTURE 片段

```markdown
## 1. 现有结构快照

| 模块 / 文件 | 当前职责 | 与本需求关系 |
|---|---|---|
| `BattleResultDialog.lua` | 结算界面入口和刷新 | 增加详情展开入口 |
| `RewardCollector.cs` | 收集战斗奖励信息 | 读取来源缓存 |
| `RewardItemPanel.lua` | 奖励项展示 | 复用或扩展为详情项 |

## 3. 目标结构

BattleResultDialog
  -> RewardSummaryPanel
  -> RewardDetailPanel
      -> RewardDetailItemPanel
```

## 7. 对话节奏样本

```text
1. 用户用几句话提出粗略需求。
2. 智能体复述目标，问 1-3 个关键问题。
3. 智能体创建工作包，先填草稿。
4. 智能体调研当前项目，必要时用只读子 Agent 并行查不同区域。
5. 智能体根据调研补 SPEC / ARCHITECTURE / DECISIONS。
6. 智能体给出实现方案和验收方式，等待用户确认。
7. 用户确认后，智能体才开始改代码。
8. 开发中出现新约束时，智能体回到文档更新和必要讨论。
9. 完成后，智能体逐条记录验收结果，ROADMAP 标记已完成。
```

核心判断：文档不是交付物的包装纸，而是让需求、项目事实、取舍和代码保持同步的工作台。
