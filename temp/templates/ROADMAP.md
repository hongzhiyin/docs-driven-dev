## 4. 详细计划

### Step 0 — 建立需求工作包

**目标**：创建 SPEC / ROADMAP / DECISIONS，并决定是否需要 ARCHITECTURE。

**任务**：
- [ ] 创建工作包目录
- [ ] 初始化文档
- [ ] 记录 ARCHITECTURE 是否需要及理由

**验收**：
1. 工作包目录存在，且文档结构清晰

### Step 1 — 澄清需求与范围

**目标**：把粗略需求转成可验收的行为描述。

**任务**：
- [ ] 补全 SPEC 一句话目标
- [ ] 补全范围 / 非目标
- [ ] 补全用户场景和功能需求
- [ ] 列出开放问题

**验收**：
1. 用户确认 SPEC 的目标、范围和非目标

### Step 2 — 调研既有实现

**目标**：理解现有代码如何支撑或限制该需求。

**任务**：
- [ ] 读取项目说明、AGENTS、已有 docs
- [ ] 查找相关实现、调用点、测试、配置、资源
- [ ] 将关键发现写入调研记录
- [ ] 将约束同步到 SPEC / ARCHITECTURE

**验收**：
1. 实现方案不依赖未验证的代码假设

### Step 3 — 形成并确认方案

**目标**：在写代码前确认实现边界、步骤、风险和验证方式。

**任务**：
- [ ] 写清实施步骤
- [ ] 写清验证计划
- [ ] 需要时新增 DECISIONS
- [ ] 等待用户确认

**验收**：
1. 用户明确同意进入实现

### Step 4 — 实施代码与测试

**目标**：按确认后的方案小步实现。

**任务**：
- [ ] <实施任务 1>
- [ ] <实施任务 2>
- [ ] <测试 / 校验任务>
- [ ] 同步 SPEC / ARCHITECTURE / DECISIONS 变化

**验收**：
1. <对应 SPEC 验收标准>
2. <测试 / 编译 / lint 结果>

### Step 5 — 验证与收尾

**目标**：确认需求完成，并留下可追溯记录。

**任务**：
- [ ] 逐条验证 SPEC 验收标准
- [ ] 记录未解决风险
- [ ] 标记 ROADMAP 完成状态
- [ ] 最终检查文档与代码一致

**验收**：
1. 用户能从文档读出需求、方案、状态和验证结果
